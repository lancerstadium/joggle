\begin{abstract}
AI workloads and emerging hardware couple computation, numerical format, and
execution strategy, so co-design changes not only a program but the compiler
algorithms that implement it; revising one decision inside such an algorithm
means editing a separately maintained implementation and rebuilding the compiler.
Joggle makes that implementation editable, a capability we call \emph{malleable
compilation}. Analyses, selectors, transformations, and generators become
ordinary typed functions in a progressive intermediate representation shared with
the programs they compile, so a researcher can derive a function with its private
helper closure, revise one internal decision, and run the copy on a separate
subject while the original stays callable and verified.
% [claim:C-locality,C-derive-storage,C-derive-control,C-derive-external] [evidence:E-locality,E-reuse-result,E-reuse-control,E-reuse-external] Author verification pending.
On every model of a ten-model campaign, a source-defined locality policy applied
without a compiler rebuild speeds the generated code, by $1.47\times$ to
$3.23\times$ with a median of $2.11\times$ and bit-identical outputs. Two derived
compiler procedures reach oracle-checked artifacts and survive unrelated
refactoring that stops an equivalent source patch from applying. On one host the
same policy also passes an unscheduled C target's lowering, by $1.42\times$,
while an optimizing compiler stays faster again: the contribution is what becomes
editable and reproducible, not code quality.
\end{abstract}

\section{Introduction}
The efficiency of an AI workload depends on the interaction between its
computations, numerical representations, and target hardware. A low-precision
format can reduce storage and arithmetic costs, but realizing those benefits
requires layouts and operations that suit the hardware
\cite{rouhani2023microscaling,wang2024ladder}. Likewise, high-performance
kernels coordinate computation with data movement and execution structure
\cite{wang2025tilelang}. These dependencies make compiler support part of
the design problem: a new numerical definition must be connected to the
representations and implementation choices through which it will execute.

These choices develop together. A portable prototype can evaluate numerical
behavior before an efficient target implementation exists, as illustrated by
Microsoft's MX emulation library \cite{microsoftMicroxcaling}. Deployment then
requires compatible storage, operations, and calling conventions. Execution
feedback may motivate a different layout and, consequently, a revision to the
compiler procedure that constructs or selects it. Compiler algorithms thus
become part of the experiment, rather than fixed tools applied to the program.

Existing systems already expose substantial control: MLIR offers partial
conversion and programmable transformations
\cite{mlirConversionDocs,lucke2025transform}, Relax connects graphs, tensor
programs, and external calls \cite{lai2025relax}, and Exo 2 and TileLang expose
scheduling and kernel choices \cite{ikarashi2024exo2,wang2025tilelang}. The
open question is what remains reusable when a researcher must revise an
algorithm inside such a system, and how the revision runs alongside its
original.

Figure~\ref{fig:overview} identifies one central obstacle and two operational
pressures along this path. The obstacle is \emph{restricted customization}: an
algorithm is easy to invoke, but the required edit lies inside its body, past
the parameters it exposes, so reusing the implementation means reaching the
parts that should stay unchanged. Two pressures then decide whether a revised
algorithm is usable at all. Under \emph{fragmented integration}, a working
revision still needs call selection, compatible data conversion, and a matching
artifact interface, so one change can require coordinated edits across several
integration sites. Under \emph{redundant work}, preparation exposes bodies no
consumer needs, or revisits the whole program after a local edit. This mismatch
between the scope of a change and the scope of the work matters most in
feedback-driven development, where every generated candidate must be compiled
and validated \cite{ouyang2025kernelbench}. Section~\ref{sec:motivation}
develops all three on a running example.

Joggle's premise is that a compiler algorithm should be reusable at body
granularity, not only callable through an interface. A researcher should be
able to revise one decision while
retaining the surrounding traversal and checks, keep the original callable,
and run the revision with its dependencies. Joggle realizes this premise
through a progressive intermediate representation shared by computations and
source-defined compiler procedures: both use the same function, type,
control-flow, and editing model, yet remain separate programs. We call the
resulting capability \emph{malleable compilation}.

Its central mechanism is a \emph{derivable compiler function}. Unified
metaprogramming exposes the bodies of source-defined analyses, selectors,
transformations, and generators to the same structural edits used for
computation. Derivation copies such a body with its private helper closure into
an inactive compiler module, where the copy acts on a separate subject while
the source stays callable. Modular resolution, replacement validation, and
invocation rollback keep the failure boundaries explicit; consumer-directed
exposure applies the shared representation to the subject, so accepted calls
remain compact while required bodies become explicit. A decision that would
otherwise live in a separately maintained implementation thus becomes an object
the experimenter can alter and run beside its original, letting competing
versions of a compiler algorithm coexist in one installation under one verifier.
Precise dependency tracking over that substrate is the natural next step and is
not part of this prototype (Section~\ref{sec:reactive}).

This paper contributes an editable implementation substrate in which a compiler
algorithm body can be retained, derived, changed, and independently executed.
Mixed-level IR, programmable transformation, and modules are established ideas;
Joggle combines their relevant properties around the algorithm body as the unit
of reuse. Concretely:

\begin{itemize}[leftmargin=1.2em,itemsep=1pt,topsep=2pt]
\item A progressive typed function representation shared by computations and
  source-defined compiler procedures, with derivation that copies a function

\section{Motivation}
\label{sec:motivation}
\subsection{From a numerical prototype to a target implementation}
Consider a block-scaled projection in which groups of encoded weights share
scale values. A portable definition decodes the weights and computes the
projection, providing a reference before a specialized kernel is available.
A target kernel instead consumes packed weights and scales in a prescribed
layout. A selection procedure must establish which calls satisfy its
requirements and retain the portable definition elsewhere. Microscaling and
compiler support for new data representations motivate this scenario
\cite{rouhani2023microscaling,wang2024ladder}; the example describes a design
problem, not an implemented MX deployment path in Joggle.

Suppose the first implementation stores scales separately from the encoded
weights. The researcher now wants to interleave them to match a different
access pattern. The decoded tensor can remain unchanged, but the packing
procedure, kernel accesses, and interface description must agree on the new
layout. By contrast, changing how a scale is chosen can alter decoded values
and requires renewed numerical evaluation. Both are small source-level
revisions, yet they affect different definitions and invalidate different
conclusions. This distinction motivates the obstacle and the two pressures in
Figure~\ref{fig:overview}.

\subsection{Restricted customization}
The existing packing procedure may already traverse eligible calls, check
shapes, and construct data conversions. Only its layout-selection branch
needs to change. A parameter solves this problem when that branch is already
configurable. Otherwise, replacing the public procedure can require
recreating its traversal and checks, while editing its shared implementation
also changes the baseline used by other experiments. The desired unit of reuse
is therefore the implementation body with a local, isolated revision.

Existing programmability makes the distinction precise. PackedFunc invokes
procedures across compiler and deployment code \cite{tvmRuntimeDocs}, MLIR
Transform composes transformations as IR, Exo 2 builds scheduling libraries
from edit primitives, and AnyDSL specializes higher-order programs
\cite{lucke2025transform,ikarashi2024exo2,leissa2018anydsl}. Revising the
implementation of an invoked procedure is a different operation from all four:
invoking a body, scripting over it, building libraries of edits, and
specializing it all leave the body itself as given.

Joggle targets that operation across source-defined analyses, selectors,
transformations, and generators: derive the procedure, retain its helpers,
edit the selection branch, and run the result without replacing the original.
Naming everything a function is insufficient; the copied body must remain
inspectable, resolvable, and executable.

\subsection{Operational pressures on a revised algorithm}
Body-level revision is necessary but not sufficient. Two further pressures
decide whether a revised algorithm is usable, and Joggle treats them as
supporting boundaries rather than as separate contributions.

\paragraph{Fragmented integration.}
A kernel that expects interleaved scales cannot consume the previous payload
even if both interfaces use the same pointer types. Call selection must choose
the matching implementation, data conversion must produce its layout, artifact
generation must expose a compatible interface, and fallback calls must keep
the portable definition. The failure need not lie inside any one component;
it can lie in their agreement. Multi-level systems connect such components
through graph, tensor, and external-call boundaries
\cite{lai2025relax,tvmArchitectureDocs,jin2020onnxmlir,onnxmlirDocs}; the
research problem is how the definitions involved in one revision are composed
and checked. Joggle keeps format, target implementation, and selection policy
as separate modules with explicit dependencies, and checks dependent call
bindings before publishing a replacement, since even an additive overload can
redirect an existing call. Agreement outside types and declarations, such as
a changed byte interpretation behind an unchanged signature, remains a
semantic obligation that the module boundary organizes rather than discharges.

\paragraph{Redundant work.}
Execution feedback then prompts the next revision. A packing change confined
to one projection need not alter unrelated bodies, whereas an updated selector
affects every call that consulted it; a local source edit does not imply a
local semantic effect. Work should follow the definitions a result actually
consumes rather than the textual edit size or a whole-program restart. Two
sources of avoidable work follow: a consumer that accepts an external
projection need not expand its portable loops, and a query whose dependencies
are unchanged need not run again. Joggle implements consumer-directed exposure
for the first and keeps the second at module granularity, which bounds what the
present prototype claims about update cost (Section~\ref{sec:reactive}).

\subsection{Design requirements and scope}
The requirements are asymmetric. Body-level derivation is the capability under
study. Module composition must preserve the copied algorithm's dependencies,
and execution must isolate compiler code from the subject it changes. Selective
exposure lets a consumer request subject detail without lowering the whole
program. Dependency-sensitive recomputation would further reduce repeated work;
establishing derivation does not depend on it.

The resulting research question is whether a compiler algorithm body can be
retained, derived, internally revised, and independently executed while its
dependencies and subject edits remain explicit and checkable. A comparative
claim about revision work additionally requires the same change through
another system's natural route, including rebuild scope and feedback cost;
Section~\ref{sec:eval-derive} reports one such control.

\section{Progressive intermediate representation and compiler functions}
Joggle makes a compiler implementation body an object of reuse. A derivation
revises a compiler definition; module resolution supplies its dependencies;
invocation applies it to a separate subject; and selective exposure may
introduce detail into that subject. These operations share a function
representation but act on different objects. Editing a compiler procedure
does not insert it into the program it compiles.

In the packing scenario, a researcher derives a selector and changes its
decision branch while retaining the original; a driver then combines
selection with preparation, keeping accepted external calls compact and
exposing required portable bodies. These are compositions of functions, not
a fixed pipeline: a storage planner revises an already prepared model without
exposing more computation. The following sections specify derivation,
visibility, and exposure before connecting them to artifact generation.

\subsection{One program, increasing implementation detail}
Joggle programs contain seven public concepts: modules, functions, blocks,
operations, values, structural types, and open attributes. There is no separate
graph object, schedule tree, pass class, or target node in the host. Calls and
structured control flow are operations. Tensor shape and numeric format are
types. Source schema fields, target facts, and analysis results are attributes
only when they are properties of represented objects rather than hidden global
state.

Progressive IR changes function bodies, not the identity of the program. A
source call may remain abstract while graph-scale transformations operate on
calls. A consumer that rejects it requests more detail, causing a portable body
to be instantiated as explicit loops and scalar operations. Alternatively, a
selection policy may bind a type-compatible external implementation without
first exposing that body. These choices are per call, so one program may contain
both states. Figure~\ref{fig:progressive} situates this mixed representation
within the system: module imports organize definitions, compiler functions
act on a separate subject, and the subject retains its common object model.
These are distinct relationships rather than successive IR levels. In the
recorded MobileNetV2 trace, selected convolutions remain external calls while
portable batch-normalization and ReLU bodies are exposed locally.

The invariant is not that all abstraction levels are equally convenient.
Rather, every exposed state remains a typed function program accepted by the
same verifier and edit API. Specialized modules may establish stronger local
contracts, but crossing that contract does not require moving the whole model
into another host representation.

\subsection{Derivable compiler functions}
\label{sec:metaprogramming}
Compiler behavior uses ordinary typed \texttt{Fn} definitions. A policy may
inspect an existing analysis as a function, invoke it with a live \texttt{Mod},
clone its definition, and edit the copy's \texttt{Blk/Op/Val} body with the
same structural primitives used on model computation. The procedure's role
comes from its signature and callers: \texttt{fn(Mod)->dict} can be an
analysis, \texttt{fn(Mod,Op)->bool} a structural edit, and
\texttt{fn(Mod)->str} a generator. No host-side pass subclass identifies
these roles.

The distinction between a procedure and its subject is concrete. Let $S$
contain an installed source definition $f$, $K$ hold derived compiler
definitions, and $P$ hold model computation; each is a value of the public
\texttt{Mod} type. A derivation $D(S,f,e;K)$ creates a fresh definition $f_e$
in $K$ by cloning $f$ and applying an edit $e$ to the inactive copy. The
source $f$ in $S$ remains callable. An execution
$\mathit{invoke}(f_e,P)$ reads or edits $P$; $f_e$ is not appended to $P$.
For a read-only query, Joggle verifies and executes a copy of $P$, then rejects
the query if that copy changed; the original $P$ is never replaced. A mutating
sequence instead backs up $P$, verifies it before execution and after each
function, retains the final state on success, and restores the backup on
failure. Code edits to $K$ and program edits to $P$ therefore have separate
rollback boundaries, not one atomic exchange. The caller must validate an
independently edited $K$ before use.

The embedding API accepts a live \texttt{Fn} handle in the existing
\texttt{query}/\texttt{run} calls, so a derived copy runs without a new host
wrapper or premature publication. A source module may instead call visible
definitions through \texttt{ir.invoke}, or install the derived definition
under ordinary module rules.

Cloning a public wrapper is insufficient when its algorithm calls private
helpers in the source module: ordinary dependency visibility prevents the
copied wrapper from calling those helpers from $K$. Let $C_{\mathrm{priv}}(f)$
be the private source definitions reachable through resolved calls from $f$.
Derivation copies $\{f\}\cup C_{\mathrm{priv}}(f)$ into $K$, rebinds private
edges to those copies, and retains ordinary explicit dependencies for public
calls. The operation either copies the closure and the requested function or
rolls back the entire derivation. This exposes the actual private algorithm, not merely its public wrapper.
Mutually recursive closures are rejected rather than partially copied, and
dynamic handle selection and opaque native bodies are not inferred into the
closure.

\paragraph{Internal edits.}
Consider the storage planner \texttt{mem.plan}, which takes a module and function.
It computes storage eligibility and lifetimes, selects reusable slots, and
attaches the plan consumed by C emission. Suppose a researcher wants a
capacity-aware choice instead of the first eligible slot, while retaining
the existing analysis and emission interface. A derivation copies the planner
and its private helpers, changes the selection predicate, and retargets the
driver to the copied function. The installed planner remains available for
comparison. This is an edit to a compiler algorithm, not a replacement kernel
in the subject program.

The edit must identify \emph{which decision} to change. Our recipe locates the
inner slot loop through its carried selection value, then follows that value's
users through the short-circuit type and lifetime tests to the assignment.
Demand and capacity are recovered from the subsequent growth comparison and
writeback, projecting branch-carried operands through their incoming values.
Thus local binding names do not select the edit site. Once these conditions
hold, the insertion uses ordinary typed IR operations
(Figure~\ref{fig:derive}). Its operands are handles recovered by the matcher,
not strings searched in the source. Replacing the old predicate's uses and erasing it
completes the local edit. The recipe rejects a changed conjunction, lifetime
comparison, selection assignment, or capacity writeback before publishing
the edited compiler module. These are algorithm-specific preconditions;
ordinary IR checking supplies type and structural validity, not a proof of
allocation safety. Numerical and storage checks therefore remain necessary
when the derived planner executes on a subject program.

\subsection{Modular management}
\label{sec:modules}
Modules compose typed definitions through explicit dependencies, visibility,
and optional native bindings. Resolution searches the declaring module and its
transitive dependencies, unifies structural types with generic parameters,
and selects the most specific unambiguous signature. Public functions are
visible to dependents; local functions remain private. Operators, analyses,
selectors, and emitters use this same resolution mechanism, not separate plugin
classes: \texttt{x + y}, for example, resolves \texttt{operator +}.

For example, \texttt{sat.c} and \texttt{sat.vm} reuse the saturating format and
materialization procedure in \texttt{sat} with distinct storage choices.
Semantic and target definitions thus compose through ordinary dependencies.

% [claim:C-module-binding] [evidence:E-module-upgrade,E-module-tests] Author verification pending.
\paragraph{Replacement checks.}
Keeping exports does not preserve bindings. Figure~\ref{fig:binding} shows
an additive facade overload redirecting an existing client call away from a
generic provider. Consequently, replacement must check both the declarations
that remain available and the declarations that existing calls select.

Joggle requires each old public signature, with generic names normalized, to
remain in the candidate. It then loads the candidate in a staged environment
and reloads the installed reverse dependents $D_m$ of module $m$. For their previously
resolved static calls $C(D_m)$, it requires
\[
  \forall c\in C(D_m),\qquad \rho_{E'}(c)=\rho_E(c),
\]
where $\rho$ identifies the qualified declaration and normalized signature,
$E$ is the installed environment, and $E'$ substitutes the candidate for $m$.
Missing, ambiguous, or changed
resolution rejects the candidate before installed files are replaced.

The check covers dependents installed in the destination root, not external
clients or runtime-selected targets. It preserves interfaces and static
bindings, not numerical behavior: a changed byte interpretation behind an
unchanged signature still needs semantic validation. Module publication and
subject editing retain separate failure boundaries.

\subsection{Consumer-directed exposure and the update boundary}
\label{sec:reactive}
\paragraph{Expose detail on demand.}
A consumer declares which calls it can accept through a typed predicate.
Accepted calls retain their abstraction boundary; rejected calls need a
compatible implementation or an explicit failure report. In the format
scenario, a supported projection can remain an external call while a
portable conversion is expanded around it. The same rule produces the mixed
MobileNetV2 trace described in Section~\ref{sec:eval-reach}.

Let $P_r$ be a verified program at revision $r$, $A(o)$ the consumer's
capability predicate, and $I(o)$ the structurally type-compatible candidates
for call $o$. A preparation policy can combine the available operations as
follows, with $i$ denoting a selected candidate:
\[
T(o)=
\begin{cases}
\mathit{retain}(o), & A(o);\\
\mathit{retarget}(o,i), & \neg A(o),\ i\text{ is external};\\
\mathit{expand}(o,i), & \neg A(o),\ i\text{ has a body};\\
\mathit{frontier}(o), & \text{otherwise}.
\end{cases}
\]
Here selection must produce an unambiguous member of $I(o)$ through a
read-only typed function. Capability specifies what the consumer accepts;
selection specifies which compatible implementation to use. Neither type
compatibility nor selection establishes numerical equivalence. That remains
an obligation of the implementation and its validation.

This policy is not a single host primitive: \texttt{opt.apply} selects and
replaces implementations, \texttt{opt.expose} expands calls according to the
consumer predicate, and their ordering belongs to the calling module.
Retargeting changes the called declaration; expansion clones the body into
the caller and rewires arguments and results, and new calls can require
another round. A frontier query identifies remaining unsupported calls for
the artifact consumer to reject. The caller supplies a round bound, since
arbitrary source bodies do not imply termination.

For a successful transition $P_r\rightarrow P_{r'}$, the host resolves the
invoked function and verifies the resulting subject after each sequence step.
The enclosing function keeps its identity while replaced operations and
values lose handle validity. Ambiguity, invalid expansion, nonconvergence, or
failed verification restores $P_r$, so a derived preparation procedure can be
tested without retaining a partially rewritten subject.

\paragraph{What precise recomputation requires.}
Exposure is selective, but work remains module-granular. \texttt{opt.expose}
repeats folding, copy propagation, dead-code removal, and unsupported-call
expansion until the module revision stabilizes. Memoization also uses that
revision, so unrelated edits can trigger scans or invalidate reusable results.

Precise recomputation would track each result's reads: a packing-body edit
affects its consumers, while a selector edit affects calls that consulted it.
Global queries and opaque native operations need conservative dependencies,
and adding an implementation can change a previous ``no candidate'' lookup, so
dependencies must include lookup sets. The representation supplies the units
such tracking needs---typed functions, explicit module dependencies, and
verified revisions---but the tracking itself is not implemented, so our
evidence covers selective exposure rather than incremental compilation.

\subsection{From checked definitions to artifacts}
% [claim:C-derive-composition] [evidence:E-reuse-path,E-reuse-result] Author verification pending.
In the storage-planner case, derivation changes the selection branch and
retargets the driver; the original and derived drivers then plan the same
prepared model, and unchanged placement and emission functions consume both
plans. A compiler decision changes while the model computation and code
generator are reused, with no further exposure step and no upgrade of the
installed planner.

Artifact modules consume the represented subject, not its compiler definitions.
The C path derives declarations, symbols, buffer shapes, byte counts, and
immutable payloads from one signature model, and the harness consumes that
descriptor rather than a second handwritten ABI; a deterministic virtual
machine supplies another execution path for tests. These paths establish
executable artifacts, not efficient ones: scalar C remains the fallback when
target tiling, packing, vectorization, or library selection is missing.

\section{System realization}
The C++20 host exposes a textual module language and embedding API, owns
structural validity, and leaves meaning and decisions to modules. It stores
\texttt{Fn/Blk/Op/Val} programs, resolves overloads, verifies edits, loads
modules, and prints programs deterministically, with no operator enumeration,
schedule vocabulary, or target lowering table.

% [claim:C-invocation-cost] [evidence:E-invocation-source] Author verification pending.
\paragraph{Invocation and isolation.}
The host resolves typed entry calls before execution. An uncached name-resolved
query copies the complete subject store, clears the copy's query cache,
verifies the copy, and rejects changes detected through its revision or printed
structure. Direct \texttt{Fn}-handle queries use the same copy-and-check path
without the persistent name cache. A mutating sequence copies the subject store
as a backup, verifies its input, and verifies the result after each function;
execution or verification failure restores that backup. This is an in-memory
rollback boundary, not concurrent publication or a transaction over external
effects. Handles carry store identity and generation to detect foreign or stale
references. Structural verification does not establish semantic correctness.

These checks have a cost. Cross-store function cloning snapshots the destination
store before copying the discovered private closure; queries and mutating
sequences likewise copy a complete store and invoke module-wide verification.
Per-function sequence timers start after the backup and input verification, and
therefore are not end-to-end invocation measurements. Cached name-resolved
queries are scoped by environment identity, environment epoch, subject revision,
function, and arguments; they do not track individual dependencies. Thus sharing
an editing interface does not imply that compilation work scales with the edited
region.

% [claim:C-module-scope] [evidence:E-module-upgrade,E-module-load] Author verification pending.
\paragraph{Module loading and replacement.}
Loading resolves dependencies from explicit search roots; a failed load rolls
back newly loaded definitions and bindings so a corrected dependency can be
retried. Installation validates a staged tree, and upgrade renames the old
directory to a backup before publishing the candidate. Validation failure
leaves installed files unchanged, but this is not a crash-atomic swap or live
reload; a failed commit attempts restoration and retains the backup.

Bundled modules exercise the boundary rather than define privileged cases:
scalar and tensor semantics, ONNX and TFLite bridges, loop and access
analyses, memory planning, C emission, and virtual-machine execution. Frontend
names end at the bridge module, and target modules publish capability,
preparation, and emission functions rather than subclasses. Continuous
integration runs on Linux and macOS with address and undefined-behavior
sanitizers, and large model artifacts are checksum-pinned outside the
repository.

\section{Evaluation}
The evaluation answers four questions in order.
\textbf{Q1} Can a decision inside a working compiler algorithm be revised
without rewriting its analysis and its consumers?
\textbf{Q2} Do the original and derived definitions stay isolated, and are
failures contained?
\textbf{Q3} Does the change reach an independently checked artifact, and what
does the same change cost through another system's natural route?
\textbf{Q4} What does the prototype cover, and what does it cost at compile
time and at run time?
Section~\ref{sec:eval-derive} answers Q1 to Q3 with two derivation studies
and their controls; Section~\ref{sec:eval-modules} adds the composition
boundary for Q2; Sections~\ref{sec:eval-reach} and~\ref{sec:eval-work}
answer Q4.

\paragraph{Evidence and conditions.}
The studies have different measurement units. Derivation uses a fixed prepared
UltraFace program and local correctness checks. Extension tasks use a fixed
Conv--Add--Relu chain and shared oracles at the revisions each table records, so
they bound a layout-and-ABI composition study rather than a general co-design
result. Model coverage aggregates checksum-pinned, revision-tagged records; it is
not a simultaneous benchmark. Runtime comparisons use one-thread controls and 20
balanced fresh-process trials per system, excluding setup and validating outputs,
and the external planner control and the same-host comparison share one macOS
arm64 host. Different jobs and revisions remain separate, and no result below
measures developer productivity or dataset-level accuracy.

\paragraph{Which system answers which question.}
One system is present for each axis it can carry, and a gap is stated rather than
implied. Rebuild scope and edit survival are measured against TVM's source route;
MLIR Transform is the fairer mechanism comparison, because its natural route
replaces a transformation's implementation body, but it stays a bounded textual
comparison with no measured data. Revision cost is measured as extension surface
over four frozen tasks, three per system with only two in common, and a task a
system cannot complete is preserved as a row rather than dropped. Run time is a
paired comparison of five systems in one job on one model, and the ten-model
campaign is Joggle-internal. ONNX Runtime generates the stored references every
other system is checked against, so its error row is a tautology and its latency
bounds a production runtime rather than a compiler.

\subsection{Revising an internal compiler decision (Q1 to Q3)}
\label{sec:eval-derive}
A configurable interface suffices when the intended choice is already a
parameter. The stronger test is to change a decision inside a reusable
algorithm without rewriting its analysis and consumers. Storage planning
instantiates the shape that Section~\ref{sec:motivation} describes for the
packing procedure: an algorithm that already supplies the traversal and
legality checks the experiment needs, while embedding the one selection rule it
must change. We derive \texttt{mem.plan(Mod,Fn)} by copying its private closure
and replacing that rule. The new rule ranks eligible slots by added capacity,
then capacity, then slot index. It retains eligibility tests, lifetime
analysis, and the interface consumed by \texttt{c.place} and C emission
(Figure~\ref{fig:derive}).

This case tests the paper's central mechanism, not the novelty of the ranking
rule; TVM's planner already prefers an adequate block by capacity. Within
Joggle, the result establishes reusable body access, isolation, and artifact
consequence. Table~\ref{tab:routes} then carries the same rule through the
pinned TVM planner's natural source route.

\paragraph{Artifact consequence.}
% [claim:C-derive-storage] [evidence:E-reuse-result]
Both planners receive the same prepared UltraFace RFB-320 program.
Prerequisite fixes for views, dynamic shape storage, and loop backedges are
shared by both variants and are not attributed to the ranking edit.
Apple Clang 17 compiles both artifacts with \texttt{-O2} and strict C99
warnings. Across two calls per variant on one recorded input, outputs are
bit-identical across variants and repetitions. The 8,840 scores and 17,680
box coordinates have a maximum absolute error of
$3.58\times10^{-7}$ against stored ONNX Runtime outputs, below the
$10^{-5}$ threshold. Declared static slots fall from 6,837,984 to 6,530,808
bytes (4.49\%), including a 24-byte increase in integer slots. This measures
declared slot capacity, excluding inputs, outputs, weights, other temporaries,
and runtime overhead; it is not a peak-memory or latency result.

% [claim:C-derive-control] [evidence:E-reuse-control]
A source-patch control extracts the same planner and private helpers and
applies the same rule as a one-hunk patch. It also avoids rebuilding Joggle
and produces the same plan. The storage reduction therefore follows from
the policy, not uniquely from structural derivation. The distinction emerges
under constructed refactorings, each of which edits something the change never
mentions (Table~\ref{tab:survival}).

Isolation regressions confirm that compiler definitions stay outside the

\paragraph{A second derivation.}
% [claim:C-derive-guard] [evidence:E-guard-result]
The same facility revises a different compiler role. \texttt{c.prepare}
exposes portable bodies and then simplifies them through a private helper.
A 70-line recipe clones the procedure with its closure, locates the single
cleanup call by its position between simplification and trimming, and
retargets it to a source-defined policy that adds interval-bounds folding
and constant-branch selection. On UltraFace the derived procedure removes 18
provably true padding guards and simplifies five more, the emitted C matches
the manually sequenced passes byte for byte, and outputs stay bit-identical
to the installed route. Median latency is unchanged (42.9 against
43.1\,ms over 20 balanced processes), consistent with the compiler already
predicting or hoisting these guards. Ambiguous drivers, duplicated or
replaced cleanup calls, and a cleanup result decoupled from the revision flag
are rejected before serialization; the installed C module is unchanged.

\subsection{Breadth (Q4)}
\label{sec:eval-reach}
The model records cover fourteen pinned ONNX models. All complete decoding and
type inference; thirteen eliminate source-frontend calls. Ten produce compiled
C artifacts that pass numerical oracles: MNIST, MobileNetV2, two SqueezeNet
variants including QDQ, ResNet18, TinyYOLOv2, UltraFace, ShuffleNetV2, DenseNet,
and GoogLeNet. TinyYOLOv3 and EfficientNet-Lite4 INT8 have conversion records
without executed C artifacts. SSD-MobileNetV1 retains 386 source calls.
XCiT-Tiny completes conversion but exceeds 227 seconds in C preparation.
Keeping these outcomes separate prevents frontend reach from being mistaken
for deployable support. TFLite MobileNetV2 provides a second frontend-to-artifact
path, within $1.1\times10^{-6}$ maximum absolute error of LiteRT.

The in-memory MobileNetV2 trace tests a different property: selection leaves
54 external Conv calls alongside 36 semantic ReLU calls, preparation retains
the external calls and prints 102 loops after exposing remaining bodies, and
the enclosing \texttt{main} handle survives while replaced handles expire.
This establishes typed mixed-state representation, not numerical equivalence
of the selected external path.

\subsection{Cost and performance boundary (Q4)}
\label{sec:eval-code}
\label{sec:eval-work}
Two costs bound the prototype: the generated code is unscheduled, and the
compiler itself is interpreted. We measure both, locate their sources, and
show that the first is addressable from source.

% [claim:C-same-host,C-locality] [evidence:E-same-host,E-locality]
A same-host comparison separates Joggle-specific cost from the cost shared by
unscheduled compiler output, and then asks whether a source-defined policy can
move it. On UltraFace with one thread, all C artifacts compiled at
\texttt{-O2}, and 20 balanced fresh processes per system in a single job,
Table~\ref{tab:samehost} reports the medians across five systems. The ordinary
Joggle artifact is within 3\% of TVM's default C-target lowering, which locates
the baseline cost in unscheduled kernel mapping rather than in Joggle: the
emitted convolution keeps the reduction innermost over a strided channel axis and
accumulates in memory.

That mapping is decided by \texttt{locality.choose}, an ordinary source-defined
function that scores axis orders and reorders through \texttt{tile.reorder}.
Applying it to the same prepared subject moves the output-width axis innermost
in 18 convolution nests, costs 1.3\,s, and requires no host rebuild. The
resulting artifact is 1.47$\times$ faster than the ordinary one and
1.42$\times$ faster than TVM's unscheduled lowering, with a bit-identical output
checksum and the same $3.58\times10^{-7}$ oracle error.

The same table bounds the claim in the other direction, and the bound matters
for how the rest of this paper should be read. ONNX-MLIR at \texttt{-O3} reaches
12.79\,ms, which is 2.17$\times$ faster than the policy-improved Joggle artifact
and 3.09$\times$ faster than TVM. An optimizing backend therefore beats both
scalar emitters, so a claim about compiler infrastructure is not a claim about
code generation. The gap to the tuned runtime narrows from 13.42$\times$ to
9.13$\times$. What remains is packing, vectorized microkernels, epilogue fusion,
and threading, and the point is where that work would live---in a source-defined
selection procedure, not in the compiler host.

\paragraph{Run time.}
The UltraFace outcome is in Table~\ref{tab:samehost}: the policy passes TVM's
unscheduled lowering and an optimizing compiler passes the policy. What follows
is whether that direction survives other models, and it is a different set of
jobs. The same policy class reproduces on a second
model and host. A generic loop
policy rewrites 54 affine-proved MobileNetV2 bodies. Across two independent
runner cohorts, its generated-C median falls from 139.679 to 102.638\,ms
(26.5\%), and from 178.796 to 131.557\,ms (26.4\%). ONNX Runtime medians
recorded beside them are 8.382 and 11.261\,ms, so the first pair retains a
12.24$\times$ gap. The repeated direction supports the policy's utility on these
inputs; the two cohorts are separate jobs and are not pooled.

Fusion supplies a counterexample to optimizing structural counts alone.
It reduces loops from 156 to 110 and C source from 192,209 to 188,244 bytes,
yet the median rises from 356.360 to 384.927\,ms. Median absolute deviations
are 1.009 and 0.531\,ms, and the adjacent runtime controls are 10.359 and
10.447\,ms. The TFLite artifact similarly executes correctly but takes
225.667\,ms against LiteRT's 6.424\,ms in its own job. Target profitability must
therefore be judged from execution rather than from structural counts, which is
itself an argument for keeping the deciding procedure editable and re-runnable.

\paragraph{Compile time.}
Interpreting source-defined compiler functions makes compilation work itself
important. A revision-scoped memoization diagnostic runs two independent
processes per variant in opposite orders on one MobileNetV2 input. Executed
source-function calls fall from 2,939,981 to 1,272,463 while 10,008 edits and
the 28.6-MB output remain unchanged; wall-time medians are 42.099 and
28.341 seconds. A separate UltraFace diagnostic replaces repeated prefix
scans in common-subexpression elimination with block-level indexing.
It preserves 597 edits and byte-identical output, with one cleanup invocation
falling from 244.26 to 11.28 seconds. Stack sampling of the planner and the C
emitter on the release build shows where the remaining time goes: allocation
and deallocation, by-value copies of string-keyed attribute dictionaries,
and types reconstructed from their text dominate the top of the stack, while
the planning logic itself is minor. The interpreter's cost is therefore a
value-representation cost, addressable by interned types, shared attributes,
and arena-allocated frames without changing the function model.

XCiT's first preparation round grows from 3,135 to 18,976 operations before
the recorded timeout: selective exposure bounds what a consumer requests,
not the cost of reaching it on a large transformer. Matched compilation-time
and peak-RSS comparisons remain future measurements. Failure tests cover
transactions and stale handles; generative tests cover parsing and legal IR
edits, not module loading, serialized frontends, or the native ABI.

\section{Related work}
Programmable transformation languages, mixed-level IRs, and modular compilers
are established, and Joggle claims none of them as new. The comparison that
matters is narrower: which compiler implementation body each system represents,
whether a user can derive an independently callable revision of that body, and
what semantic and rebuild obligations remain afterwards.

\subsection{Programmable compiler implementations}
\label{sec:related-transform}
% [claim:C-related-transform] [evidence:E-transform-script,E-transform-implementation] Author verification pending.
MLIR Transform represents transformations as IR over a separate payload,
with typed handles, effects, and failure semantics
\cite{lucke2025transform,mlirTransformDocs}; its scripts admit inlining,
simplification, and introspection. The implementation boundary nevertheless
remains: the official extension tutorial implements an action in C++ through
\texttt{TransformOpInterface::apply} \cite{mlirTransformTutorial}, and revising
that function differs from rewriting the script that invokes it.

% [claim:C-related-exo] [evidence:E-exo-schedule] Author verification pending.
Exo 2 makes scheduling libraries programmable through inspection, action, and
reference primitives, with versioned cursors that survive edits
\cite{ikarashi2024exo2}; library construction and structural references are
thus established techniques. The difference concerns the object being edited:
Joggle applies its function-body operations to source-defined analyses and
generators as well as model code.
It checks structural validity; semantic preconditions remain the algorithm's
responsibility. In the storage case the edited branch belongs to the planner,
not to a model loop or the invoking sequence, and derivation yields an
independently callable version without a new native hook. The difference lies
in which body is editable, not in stronger transformation guarantees.

% [claim:C-related-staging] [evidence:E-anydsl-specialization] Author verification pending.
AnyDSL expresses DSL semantics through higher-order closures and specializes
them by online partial evaluation \cite{leissa2018anydsl}; its shallow
embedding exposes no embedded syntax tree for later rewrites. LMS supplies
staged abstractions \cite{rompf2016lms}, and Weval specializes an existing
interpreter \cite{fallin2025weval}. Specialization resolves supplied inputs
and abstractions, whereas Joggle's planner edit changes a decision inside a
represented algorithm that still needs its own semantic validation.

TVM's PackedFunc provides type-erased calls and higher-order callbacks across
languages, compiler passes, and deployed functions \cite{tvmRuntimeDocs}.
The call interface does not describe the callee's body. Joggle combines
structurally checked calls with inspectable source bodies, separate compiler
and subject modules, and verified mutation (Section~\ref{sec:eval-derive}).

\subsection{Module boundaries and extensibility}
JastAdd and Polyglot modularize language definitions and analyses
\cite{ekman2007jastadd,nystrom2003polyglot}. Spoofax composes language
specifications across syntax, semantic analysis, transformation, generation,
and editor services \cite{kats2010spoofax}. Nanopass organizes compiler
construction through small languages, and MAGIK exposes compilation to
application-specific semantics and control
\cite{sarkar2005nanopass,engler1997magik}. These precedents motivate reuse of
compiler definitions across roles, beyond packaging an individual pass.

Klopp et al. attach module semantics directly to an IR through typed Datalog
modules with required and provided relations and separate compilation
\cite{klopp2024datalogmodules}. Joggle's module unit holds typed functions and
dependencies checked on installation and replacement; reverse-dependency
checks govern publication, and program-edit transactions govern execution on
a subject, whatever the function's compiler role.

MLIR supports runtime-defined dialects, IRDL definitions, external interface
models, and partial conversion
\cite{mlirDynamicDialectDocs,mlirIrdlDocs,mlirInterfacesDocs,mlirConversionDocs}.
xDSL couples Python prototyping to MLIR through shared textual IR and IRDL
definitions. Its sidekick workflow can insert a prototype into an existing
compilation flow and return to MLIR for later processing \cite{fehr2023xdsl}.
Joggle instead centers source extensions on typed function definitions with
shared resolution and execution rules across compiler roles, leaving
domain-specific checks and native bindings explicit.

\subsection{Mixed representations and deployment}
TVM's IRModule composes Relax functions, tensor programs, and external calls
for cross-level optimization \cite{lai2025relax,tvmArchitectureDocs}.
Relax's \texttt{call\_tir} and library-call primitives connect functional graph
semantics to destination-passing implementations. Partial lowering, analysis
feedback, and joint caller/callee rewrites make these boundaries active
optimization interfaces, not merely a shared container \cite{lai2025relax}.
MLIR's common operation, region, block, and value structure likewise permits
multiple dialects in one program
\cite{lattner2021mlir,mlirLangRefDocs,mlirConversionDocs}.
Consequently, mixed abstraction levels do not require abandoning specialized
invariants or converting an entire program in one step.

Joggle combines this local coexistence with a common function-body model for
computation and source-defined compiler procedures: a consumer can retain a
call, select an external implementation, or expose its portable body, and the
procedures making those choices can themselves be derived and revised. This
connects implementation choice to compiler-body customization; it does not
provide the recomputation proposed in Section~\ref{sec:reactive}.
ONNX-MLIR \cite{jin2020onnxmlir} and IREE \cite{ireeDocs} are complete-system
comparisons, so Joggle's evaluation follows the complete-artifact boundary.

\subsection{Kernel construction and automatic optimization}
Lift, RISE, and Elevate make transformation strategy explicit
\cite{steuwer2017lift,steuwer2022rise}; Halide and Tiramisu separate algorithms
from schedules \cite{ragankelley2013halide,baghdadi2019tiramisu}; TensorIR,
Hidet, and TileLang expose blocks, tiles, threads, and data movement
\cite{feng2023tensorir,ding2023hidet,wang2025tilelang}; Exo externalizes target
instructions, memories, and trusted rewrites into user code
\cite{ikarashi2022exo}, and sparse systems expose format and data-movement
choices \cite{daghero2025sparse}. Joggle addresses how such choices compose
with model recognition, portable definitions, compiler policies, and artifact
generation; scheduling quality itself is the gap Section~\ref{sec:eval-code}
measures. Ansor searches tensor programs; Roller constrains shapes to hardware-friendly
tiles; Welder jointly schedules operators through a tile graph; Ladder couples
custom datatypes with storage, access, conversion, and scheduling
~\cite{zheng2020ansor,zhu2022roller,shi2023welder,wang2024ladder}. TASO, Tensat,
Glenside, Mirage, and Axon enlarge the transformation space through generated
substitutions, equality saturation, access-pattern rewriting, or multi-level
superoptimization
~\cite{jia2019taso,yang2021tensat,smith2021glenside,wu2024mirage,kothari2026axon}.
ACT generates instruction selection and scratchpad allocation from tensor-ISA
semantics, while ATLAAS lifts RTL behavior toward those specifications
~\cite{jain2026act,gao2026atlaas}.

These works improve generation or selection within specific search spaces
and target models. Joggle makes the selection procedure a replaceable typed
function and checks its structural edits before publication, separating a
policy's integration from its optimization quality; it implements none of
those search or synthesis algorithms.

\subsection{Hardware--representation co-design and edge inference}
DORY, MCUNet, Ladder, and sparse-MCU systems treat datatype, encoding,
memory organization, kernels, and compiler integration as one systems result
\cite{burrello2021dory,lin2020mcunet,wang2024ladder,daghero2025sparse};
TensorFlow Lite Micro, ncnn, and IREE supply deployment baselines
\cite{david2021tflm,ncnnProject,ireeDocs}, and FlashInfer shows the same
vertical pressure in attention kernels \cite{ye2025flashinfer}. Joggle uses
edge inference as a demanding evaluation domain, not as a scope restriction.

\subsection{Generated policies and compiler reliability}
LLM-aided optimizers depend on compilers, profilers, and oracles to admit
generated mappings or kernels \cite{hong2025autocomp,mai2026argus}, and
compiler fuzzing and bug studies show a large semantic failure surface
\cite{liu2023nnsmith,ma2023hirgen,zheng2021compilerbugs,xiao2022metamorphic}.
Joggle's transactional edits and capability queries delimit the structural
effects of a generated proposal; numerical correctness remains the oracle's
role (Section~\ref{sec:eval-work}).

\section{Discussion and limitations}
\paragraph{Where customization belongs.}
When a policy argument expresses the desired change, it avoids matching an
implementation body. Derivation reaches decisions outside that interface,
but requires algorithm-specific structural preconditions. The source-patch
control obtains the same artifact, and TVM's source route reaches its own
checked artifact after a compiler rebuild; maintenance cost remains unmeasured
on either side. The planner edit and MobileNetV2 trace demonstrate complementary uses of the
representation, not a combined benefit.

\paragraph{Shared structure and specialized meaning.}
Common structure does not make domain semantics interchangeable: repacking
bytes behind an unchanged pointer signature passes resolution yet can violate
a kernel's expectations, so modules and algorithm-specific oracles establish
such properties. Joggle shares editing facilities, not domain semantics.

\paragraph{Editability and cost.}
Derivation copies helper closures, and revision-keyed snapshots consume memory.
Selective exposure retains accepted calls, yet repeated scans and coarse
invalidation can dominate preparation, as the XCiT timeout illustrates. The
sampled profiles show that the interpreter's overhead is representational,
not structural: the same typed function model can be executed over interned
types and shared attributes. Dependency-sensitive recomputation becomes
worthwhile only once that baseline is competitive, which fixes the order of
future work.

\paragraph{Deployment and evidence.}
Model oracles establish agreement on recorded inputs, not dataset-level
accuracy, and support for dynamic shapes, stateful execution, concurrent
devices, and distributed placement remains incomplete. The same-host comparison
above shows what the substrate does and does not buy: loop reordering is now a
measured source-level change, and the rest of the familiar kernel
checklist---register accumulation, GEMM mapping, epilogue fusion,
parallelization---remains, each likewise a source-defined selection or emission
procedure. The mechanism evaluated here is the route by which that work enters
and is compared; it is not a claim that the route has been walked to its end.

\section{Conclusion}
Joggle treats a source-defined compiler algorithm body as a reusable program
artifact. A derivation copies the selected definition and private helper closure,
admits an internal structural edit, and executes on a separate subject while
the original remains callable. Module resolution, verification, and rollback
make that boundary explicit; selective exposure applies the same representation
to subject detail. The storage-planner and preparation cases carry such edits to checked
artifacts, while the source-patch control and current compilation and runtime
gaps bound the claim. One matched external control shows the same rule reaching
a checked artifact through TVM's source route with a compiler rebuild that
derivation avoids and with faster native planning. The prototype's own
compilation and inference costs, and dependency-sensitive recomputation, bound
what we claim today; each is work this substrate now hosts as an ordinary
source-defined function rather than as a change to the compiler itself.
