# Design 0002: Fn values

Status: accepted

## Problem

Joggle first supported fn types only through values that reference a
declared fn:

```joggle
fn apply<T, U>(input: T, body: (T) -> U) -> U;
fn convert(input: i8) -> i16;
fn use(input: i8) -> i16 {
  return apply(input, convert);
}
```

Adding inline fn expressions must not create a hidden mod declaration
for every lambda: that would make formatting, declaration digests, overload
reflection, and native compatibility depend on synthesized names. Carrying
untyped syntax as metadata would postpone errors and create a second
expression system. Both approaches are rejected.

## Accepted surface

A capture-free typed lambda is an expression:

```joggle
(x: i8) => extend(x)
(x: tensor, w: tensor) -> tensor => relu(conv2d(x, w))
```

Parameter annotations are mandatory. The result type is inferred from the
body when a callable context supplies it. The optional `-> type` annotation
supplies that context when a compiler fn accepts the general `fn` domain, as
transformation services do. If both forms of context exist, they must agree.
The body is then materialized against the selected result type, so the
annotation cannot conceal an incompatible expression.

The body uses the normal expression grammar and normal overload resolution.
There is no pattern-expression parser, Lambda declaration, Region wrapper, or
builder-only syntax.

The first implementation is deliberately capture-free. A reference in the
body resolves to a lambda parameter or mod declaration; literals remain
normal Known expressions. Referring to any outer local is a diagnostic.
Capture semantics require a separate design decision because they affect ABI,
serialization, and transformation equality.

## One callable type

Both declared references and inline fns have the existing type:

```joggle
prelude.callable<[input types], [result types]>
```

Fn type syntax remains its readable source form:

```joggle
(i8, i8) -> i16
```

No public `Lambda`, `Closure`, `Pattern`, or `Callable` class is added. C++
continues to inspect an inline callable as `Fn`.

## IR representation

A callable `Val` has one of two definitions:

1. a reference to an exact `Mod::FnDecl`;
2. an immutable inline `Fn` body.

This is a property of `Val` storage, not a new IR owner. The inline body is
anonymous and therefore does not appear in `Mod::members()`, overload
lookup, or the declaration digest. It contributes structurally to the owning
fn and therefore to the complete mod digest.

The public query becomes:

```cpp
std::optional<Mod::FnDecl> Val::referenced_fn() const;
std::optional<Fn> Val::inline_fn() const;
```

Exactly one is present for a callable literal. Existing callers that only care
about declared identity continue to use `referenced_fn()`.

## Construction and verification

The parser records a lambda with parameter names, their normal type
expressions, and one normal body expression. Parameter types participate in
overload filtering; the body is checked after one overload is selected rather
than speculatively executed for every candidate. During materialization:

1. parameter and optional result type expressions are resolved in the
   surrounding mod scope;
2. those annotations are unified with any surrounding callable type;
3. a fresh anonymous `Fn` is created in the same compiler closure;
4. its arguments are bound to the lambda parameter names;
5. the body expression is materialized by the same bidirectional expression
   machinery used for named fns, including nested generic calls;
6. its result is checked and the body is verified;
7. the owning fn receives an inline callable `Val` with the derived
   `prelude.callable` type.

The implementation must refactor the named-fn materializer around a
shared concrete signature/body engine. It must not copy call-resolution logic
into a lambda-only compiler.

Verification checks that:

- the callable type exactly matches the inline fn inputs and results;
- the inline fn uses only mods in the owner's closure;
- its values and blocks belong to the inline fn;
- it contains no outer residual value;
- recursively nested inline fns are acyclic by ownership;
- declared references still match their exact declarations.

## Formatting and identity

A single-expression inline fn formats as the source lambda syntax. The
formatter derives parameter and result types from the verified `Fn`; it
does not preserve an untyped syntax blob.

Canonical mod identity includes callable type, parameter order, operations,
control flow, known constants, and nested callable values. Parameter spelling
is not semantic identity. Canonical formatting assigns deterministic local
names, as it already does for materialized fns.

## Staging

A lambda expression constructs a callable value; it does not execute it.
Passing it to an ordinary higher-order call leaves that call Residual.

Passing a lambda to a compiler fn whose parameter has the `fn`
domain constructs a verified anonymous `Fn`. Explicit `@` invocation
passes that object directly as an execution value; it is never serialized
through scalar `ParamVal`. A compiler fn may return the same
`Fn`, which can be bound and passed to a later `@` call. Fn-valued
calls are not entered in the scalar hermetic-evaluation cache.

This direct path is required for the later transformation API:

```joggle
@transform.replace(
  model,
  (x: value) => step(step(x)),
  (x: value) => twice(x),
)
```

The call remains one ordinary overload. `replace` is not a declaration form.

## Implementation gates

1. [complete] Add inline-fn storage to callable `Val` and exact
   verification.
2. [complete] Refactor fn materialization around a concrete anonymous
   signature.
3. [complete] Parse, validate, and canonically format capture-free typed
   lambdas.
4. [complete] Materialize lambdas in ordinary higher-order calls.
5. [complete] Extend explicit `@` invocation to pass typed `Fn` values
   directly.
6. [complete] Add source round-trip, ownership, ambiguity, cloning,
   nested-callable, and negative-capture coverage.
7. [complete] Add optional result annotations and propagate their expected
   type inward through nested generic calls.

Each gate must keep all existing tests passing. No rewrite API is introduced
until callable values complete this sequence.
