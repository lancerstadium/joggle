# Design 0005: Source frontends and NN semantics

Status: accepted; conversion implementation pending

## Decision

An external format is not Joggle's neural-network IR. Each frontend has three
separate responsibilities:

1. a byte reader owned by the format package;
2. a versioned source schema containing only declarations, defaults, and the
   shape equations needed to type imported calls;
3. ordinary pass equations that normalize source calls into the shared `nn`
   vocabulary.

For ONNX these owners are `onnx`, `onnx_schema`, and a pending conversion Mod.
The algorithms live in `nn`; Tensor supplies only logical construction and
overloaded access.

## Why source calls remain visible

Directly translating bytes into `nn` would discard opset and attribute meaning
before it can be audited. Treating ONNX nodes as final NN semantics would couple
all optimization to one exchange format. A source-schema call preserves the
format contract long enough for an explicit conversion pass to validate and
normalize it.

This is the useful distinction behind the generated ONNX operation layer in
[ONNX-MLIR](https://arxiv.org/abs/2008.08272), but Joggle avoids turning every
schema into a compiler-built-in C++ class. The importer resolves ordinary Fn
declarations and the conversion is an ordinary pass over ordinary Fn calls.

## Multi-frontend rule

TFLite will own a TFLite reader and TFLite schema. It will not import ONNX
declarations, share an ONNX-specific adaptor, or place TFLite option decoding in
`nn`. The only convergence point is the frontend-neutral call produced after
conversion. A format-specific feature with no `nn` equivalent remains visibly
source-specific until an extension package defines its meaning.
