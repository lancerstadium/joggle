# Design 0005: Signature-driven ONNX import

Status: accepted

## Decision

ONNX is an optional Mod, not a compiler subsystem:

```joggle
joggle 1;

mod onnx@5.0.0 {
  import arith@1 as a;
  import quant@2 as q;
  import tensor@4 as t;

  fn read(input: bytes, name: string = "model") -> mod;
  // Node schemas and semantics are ordinary fns below this boundary.
}
```

`read` is an explicitly staged native fn because protobuf decoding and Mod data
creation cross the host boundary. It returns the same `Mod`, `Fn`, `Op`, and
`Val` representation used by source programs. Compiler core gains no frontend
base class, operator registry, graph object, dialect, attribute store, or
lowering interface.

## Schema authority

The linked source Mod is the only operator schema. For each `NodeProto`, the
decoder looks up `onnx_mod.overloads(node.op_type())`, binds the serialized
inputs and attributes against each declaration, and accepts one unique match.
Parameter domains decide how an attribute or INT64 initializer is decoded.
Declaration defaults handle omitted ONNX attributes. The ordinary compiler
evaluator instantiates generic parameters and evaluates dependent result Types.

Consequences:

- adding an ordinary node does not add C++ dispatch;
- shape inference lives in staged source fns, not native formulas;
- overload resolution handles optional forms such as Conv with or without
  bias;
- an unknown attribute or ambiguous/missing overload is a deterministic import
  failure; and
- native changes are reserved for new serialized representations, not new
  tensor vocabulary.

The decoder still validates model-level structure, opset profiles, tensor
payload storage, graph naming, and metadata consistency. Those are properties
of the file boundary rather than operator semantics.

## Semantic normalization

The imported graph initially preserves ONNX names for provenance and source
fidelity. A bodyful ONNX fn is then ordinary materializable code. Generic
inlining can remove `Dropout`, expand `Relu` to `tensor.map`, and expand `map`
to domain `tensor.map` and overloaded `[]` without inspecting any of those names.

The first compute-heavy body is rank-two `MatMul`. It composes explicit-domain
`tensor.map`, ordered `tensor.reduce`, overloaded coordinate/Tensor `[]`, and
generic scalar `zero`, `*`, and `+`. Materialization specializes calculated
shapes through the lexical compiler bindings inherited by nested lambdas. It
does not introduce a MatMul node in compiler core. Batched and broadcast ONNX
MatMul semantics are not implemented yet.

This is only the entrance to the intended normalization. Compute-heavy ONNX
fns must acquire source bodies over the small tensor calculus. Fusion is then
producer-consumer cancellation such as

```text
map(S, f)[p] = f(p)
```

rather than a `Conv+Relu` pattern or a fused operator catalog.

## Reference evidence

The pinned FLOAT artifact is ONNX Model Zoo SqueezeNet 1.1 opset 7:

| Field | Audited value |
| --- | --- |
| SHA-256 | `1eeff551a67ae8d565ca33b572fc4b66e3ef357b0eb2863bb9ff47a918cc4088` |
| Graph | 66 nodes, 53 initializers |
| Input / output | `f32[1,3,224,224]` / `f32[1,1000]` |
| Imported Fn | 52 Constants + 66 semantic calls |

The pinned QDQ artifact is SqueezeNet 1.0 opset 13 with SHA-256
`4a567dd7542ef440890d57268fabf47211174c593d7a1837bd7f16a1067169e7`.
It imports 228 typed constants and 171 standard ONNX calls, including 39
QuantizeLinear and 91 DequantizeLinear calls. Tests fix payload digests,
dependent result Types, call distributions, locations, bundle identity, and
repeated-import determinism.

The optional runtime gate reconstructs both graphs from Joggle state and
compares them with the originals under ONNX Runtime. This validates import
fidelity; it does not yet prove tensor-calculus execution or optimized code
generation.

## Provenance and ownership

Node names and ordinals are optional `Loc` provenance on ordinary calls. They
do not influence semantic identity. The original ONNX bytes and canonical
initializer payloads are immutable, content-addressed Mod data and survive
bundle installation and locking.

Compiler core remains protobuf-free. The optional ONNX native library uses the
system protobuf runtime and a hash-pinned official schema. Generated protobuf
C++ is build output.

## Gates

- [x] Preserve source locations through public editing and inlining.
- [x] Import both exact, hash-pinned reference profiles transactionally.
- [x] Preserve source and initializer payloads in installable Mod bundles.
- [x] Replace per-operator native dispatch with source-signature binding.
- [x] Evaluate dependent output shapes in staged source fns.
- [x] Preserve every standard reference-model node as an ordinary call.
- [x] Expand bodyful Relu and Dropout through generic inlining.
- [ ] Give all required compute-heavy ONNX fns tensor-calculus bodies.
- [x] Give rank-two MatMul a materialized and verified tensor-calculus body.
- [x] Recurse through nested lambdas and cancel concrete typed
  `map(shape, ...)[...]` equations without an ONNX-name matcher.
- [ ] Generalize Tensor equations over element Types and shapes.
- [ ] Demonstrate name-independent producer-consumer fusion numerically.
